PV-MEPCG / PulseVision — MISSING OUTPUTS REPORT

Purpose
-------
Every deliverable named in the source documents that this project could NOT
produce is recorded here, with the technical reason. Ground rule 1: a number is
never invented and a gap is never silently omitted. Ground rule 7: this file is
created empty in Phase 01 and APPENDED TO as gaps arise — it is never written at
the end from memory, because by then the reasons are forgotten.

A `[-]` (skipped) checkbox in `Docs/todo.md` REQUIRES a matching entry here and
a matching entry in `Docs/note.md`.

Entry format
------------
[YYYY-MM-DD] <task id> — <deliverable that is missing>
  Reason: <the technical reason it could not be produced>
  Impact: <what claim or figure is affected downstream>

[2026-08-26] T20.5 — PhysioNet 2016 held-out external test set (301 validation records)
  Reason: All 301 records in `dataset/archive (3)/validation/` are BYTE-IDENTICAL
    (SHA-256 of raw bytes) to 301 records already present in training-a..f. They
    contain no audio the training corpus does not already contain. Those 301
    twins belong to 205 derived subjects, and those 205 subjects account for
    1,108 of the 3,240 training records — so constructing a subject-disjoint
    holdout from this folder (rule 3) would remove 34% of the primary track's
    training data in exchange for a test set of previously-seen material.
    Verified in Phase 09 (physionet_subject_derivation.csv) and Phase 17
    (duplicate_report.csv: 301 rows, method=raw_sha256, decision=drop).
  Impact: EXP-A1 and EXP-A2 report repeated 5x5 subject-grouped cross-validation
    only; `external_test` is null for both in configs/experiments.yaml. No
    single-number "held-out test" figure is claimed for PhysioNet anywhere in
    the thesis, paper or dashboard. External validation for the binary track is
    carried by EXP-D1 (PhysioNet -> CirCor), which uses a genuinely independent
    corpus. Decision confirmed with the user 2026-08-26.


[2026-08-26] T29.3 / T29.4 / T29.7 — PP-09 `preprocessing_ablation.csv` (deferred, not skipped)
  Reason: The task asks for features to be extracted and a baseline model trained
    under each of the four filter x normalization configurations. Neither input
    exists at Phase 29: the locked 138-feature extractor is built in Phases 31-42
    and the fold-safe CV pipeline, metrics module and baseline models in Phases
    43-46. The only way to produce PP-09 on schedule would be to write a
    throwaway feature set and model for this one table, which would place metrics
    in a deliverable that the actual pipeline never produced — the failure mode
    ground rule 1 exists to prevent.
  Impact: T29.7, the Phase 29 gate, is blocked on the same gap: its PP-07 and
    evidence-registration clauses pass, its "the ablation ran all four
    configurations" clause cannot until PP-09 exists.
    PP-09 is registered in the evidence index with status=missing rather
    than omitted, so the gap is visible. The four arms ARE defined and verified
    (T29.2 complete): `preprocessing_ablation_grid.csv` holds their config hashes
    and cache directories, and all four were confirmed to produce distinct
    preprocessed signals, so the ablation is ready to run rather than merely
    planned. Re-entry point: immediately after Phase 46, using the real 138
    features, the Phase 44 fold-safe pipeline and a baseline model, so PP-09 is
    comparable with every other metric in the thesis. Decision taken with the
    user 2026-08-26. No preprocessing claim anywhere may cite an ablation result
    until that run exists — the justification for the shipped configuration is,
    until then, the design argument in Docs/note.md and the T24/T26 measurements,
    not a measured metric delta.

[2026-08-27] T52.2 / T52.3 / T52.4 / T52.5 — M9, the optional 1D-CNN deep baseline
  Reason: Decided OUT OF SCOPE by the user on 2026-08-27, against the measured
    cost of the classical stack rather than against an assumption. This machine
    is CPU only — 4 logical cores, no CUDA device — and both source documents
    list the 1D-CNN as Optional.
    The measurement that settled it: all eight classical models together fit one
    fold of the 3,240-record PhysioNet track in 41.1 s wall clock (M1 0.23 s,
    M2 0.05 s, M3 1.34 s, M4 5.84 s, M5 27.37 s, M8 6.31 s; M6/M7 add ~163 s
    each because they refit their members over an inner CV). The full 5x5
    grouped fold map is therefore ~17 minutes for the classical stack.
    A 1D-CNN over fixed-length preprocessed segments is not comparable to that
    on this hardware: it trains on raw waveform segments rather than on 138
    precomputed scalars, so a single fold is hours and the full fold map is days,
    with no GPU to shorten it. Running it on a reduced fold map instead would
    break the comparison the model exists to support — T52.4 requires it to be
    trained under the SAME fold map as the classical models, or its accuracy
    cannot be placed beside theirs.
    It would also add an unpinned deep-learning dependency (PyTorch or Keras,
    neither currently in requirements/) that would have to be re-verified to
    install and run on Windows + Python 3.11.9 with no compiler toolchain.
  Impact: No deep-learning baseline appears in the model comparison. The
    complexity trade-off argument (T25/T26, Phase 75) rests on the eight
    classical models only, and the thesis limitations section must state that a
    deep baseline was excluded for hardware reasons rather than tested and
    rejected on performance. No claim anywhere may compare PV-MEPCG against a
    CNN, or describe the classical stack as outperforming one.
    M9 remains declared in configs/models.yaml with `in_scope: false` so the
    exclusion is visible in the model registry (`registry_frame()` reports it as
    not implemented with this reason) rather than looking like an oversight.
